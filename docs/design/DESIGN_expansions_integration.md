# Design — Removal Expansions Integration (Distractions · Belongings · Shadows/Reflections)

**Date:** 2026-10-14
**Author:** UI/UX design lead (§10 authority)
**Commission:** Owner request — design how three expansions of the removal feature integrate into the shipped flow. Research first; no app code is being written from this doc yet. It is the design half of a combined implementation plan.
**Scope (owner's, fixed):** (1) distractions removal — bins, poles, cars, wires, auto-detected like people; (2) belongings removal — a removed person's bags and similar go with them; (3) reflections and shadows of a removed person handled as part of that person's removal.
**Binding constraints:** product facts in `PEOPLEGONE_REQUIREMENTS.md`; the honesty rule (copy claims only what the shipped capability does, at the strength the evidence supports); the owner's quality mandate for this work — **defaults are conservative, nothing new is removed without the user's review, and the keeper guarantee extends rather than dilutes.**
**Assumption discipline:** a technical feasibility pass is running in parallel and its results are not in my hands. Every element below that depends on unconfirmed capability is marked **[ASSUMPTION]** or listed as an open question (§7). Nothing marked as an assumption is a settled ruling.

---

## 1. Research — how the field presents this (observed, paraphrased, sources named)

- **Adobe (Photoshop / Lightroom / Camera Raw) — Find Distractions.** Detection is organised by **category**: People; Wires and Cables; and a General Distractions set (dozens of object types — vehicles, poles, signs, bins, animals) of which the UI lists **only the categories actually found in the photo**. Found items are highlighted with colour-coded overlays on the canvas; categories can be toggled wholesale (untick a category to keep everything in it), and individual areas can be added or protected with plus/minus brushes. Two category treatments differ instructively: **wires are removed with a single click** (no per-item review offered), while the **People mode explicitly offers refinement of who stays**. Adobe's own category descriptions treat a person's **cast shadow as part of the person**. Sources: Adobe's feature coverage (PetaPixel, 2024-10-14), hands-on guides (Phlearn; Glyn Dewis), a category reference (PSD Vault guide, 2026).
- **Google — Magic Eraser (Pixel / Google Photos).** The **suggestions model**: detected candidates (background people, power lines) are highlighted on the photo; the user can erase all, erase one at a time, or **overrule a suggestion and keep the item**. Suggestions are framed as exactly that — proposals the user disposes of. Sources: Google Store's Magic Eraser article; Android Authority / XDA hands-on coverage.
- **Samsung — Object Eraser.** Objects are tapped or circled per item. Shadows and reflections are **separate whole-image actions** ("Erase shadows" / "Erase reflections"): tap once and the app analyses and removes *all* detected shadows or reflections in the photo, with no per-item review — launched as a Labs (beta) feature, with reviewers consistently reporting partial, hit-or-miss results. Sources: Android Police; How-To Geek; ZDNET hands-on.
- **Apple — Clean Up.** Detected items are highlighted in place on the photo; one tap removes. No categories, no list — the suggestion *is* the canvas highlight. (From this project's earlier research passes.)
- **SnapEdit.** Auto-detect outlines every object and person; each is tapped to select/deselect; a Select All exists. Flat per-item model, no categories. (Vendor how-to, snapedit.app.)
- **TouchRetouch.** Category-first *tools* (Objects, Lines, Meshes, Blemishes); lines are auto-detected on tap. Manual-first overall — the opposite end of the automation spectrum from Adobe. (Walkthroughs surveyed in Review 05's research.)

**What the field teaches, distilled:** (a) non-people items are always presented *on the canvas and/or as per-item chips*, never as a blind global switch — except Samsung's shadow/reflection buttons, which are also the field's most-criticised for overreach; (b) category-level bulk actions exist as *convenience layered over per-item review* (Adobe), not as a replacement for it; (c) the strongest products treat a person's shadow as part of the person (Adobe); (d) nobody of consequence shows the user a confidence number — uncertainty is handled by *thresholds and presentation*, which is where design must do the same work.

## 2. The integration principle

S4's confirm gate is this product's trust core: **everything that gets removed is something the user saw, itemised, before it was removed.** The expansions pass through that gate or they do not ship. No new screens, no new steps, no settings. S4 grows from one group of items to up to three kinds of items; everything else in the flow changes only where copy must stay truthful.

## 3. Rulings — distractions in S4

- **X1 — One review surface, grouped.** S4 keeps its current structure (canvas, status sentence, tray, confirm). Below the People tray, a **Distractions group** appears **only when at least one showable distraction exists** (the Adobe pattern: never present an empty category). Group header: "Distractions" + count. The group never appears above People, and S4's title stays "Review people to remove" — people remain the product's headline act. **[ASSUMPTION: the detector returns a category label per item from a small closed set — car, pole, bin, wires, sign, other. The chip design below needs one short noun per item; "other" is an acceptable label.]**
- **X2 — Chips mirror people chips.** Each distraction is a chip in a horizontally scrolling tray, same construction as PersonCard: a real crop of the item from the photo, a label ("Car", "Pole", "Bin", "Wires"), and a state pill ("Remove" / "Keep"). Same tap-to-flip, same canvas highlighting. One visual system for every removable thing; a user who learned S4 already knows this screen.
- **X3 — Default: KEEP (opt-in removal).** Every distraction starts as Keep. This is a deliberate deviation from Adobe/Google (suggestions pre-marked for removal), taken for three stated reasons: those are editors where removal is free, instant and undoable in place; PeopleGone spends a server job and the user's trust on a single confirm. A false-positive *person* costs a re-run; a false-positive *distraction* can be the user's own car, sign, or stall — property, removed on the app's opinion. And the owner's mandate for this work is conservative defaults. The status sentence and confirm button (X5) make inclusion explicit, so opt-in never hides.
- **X4 — Category convenience, per-item truth.** The group header carries two text actions: "Remove all" / "Keep all" (the Adobe category toggle, translated). They set every chip in the group at once; every chip remains individually flippable afterwards, and the canvas shows the result immediately. No category sub-lists, no filters, no per-category rows in v1 — with a handful of items per photo, one labelled group is the honest scale. **[ASSUMPTION: typical showable distractions per photo stay in single digits. If the tech pass shows busy street scenes returning 15+, this ruling gets revisited with counts, not vibes.]**
- **X5 — Status sentence and confirm count everything being removed.** The existing sentence ("@count people will be removed · @count people protected") gains a distractions clause only when ≥1 distraction is included: "3 people and 2 distractions will be removed · 1 person protected". Confirm label likewise: "Remove 3 people" today; "Remove 3 people + 2 distractions" when distractions are included. Keep-all-people with distractions included is a valid confirm (the button must not die in that state — Review 04 F3's lesson applies to the new combinations: every reachable state of S4 has a working primary or an explicit exit).
- **X6 — Low-confidence distractions are not shown at all.** No "not sure" presentation for objects. A doubtful person is still plausibly the app's core subject; a doubtful bin is noise wearing a chip. Below the show-threshold, the item does not exist in the UI. (The threshold itself is the tech pass's calibration — OQ2.) People's existing score-band treatment is unchanged by this doc.
- **X7 — Canvas language stays binary and consistent.** Included-for-removal items (any kind) read in the removal colour; protected people read emerald, as today; kept distractions take a thin neutral outline (they are not "protected", merely not selected — emerald is reserved for the protected set, §4). Belongings read as part of their person (X9). **Tap priority where items overlap:** people first (smallest containing box among people), then attached belongings, then distractions. A tap toggles the winning item only; anything underneath stays reachable through its chip. The person always wins a contested tap — people are the primary layer of this app, and a mis-tap must err toward the item the user most likely meant.

## 4. Rulings — belongings

- **X8 — A belonging is a property of its person, not a new item kind.** When a person is marked Remove, their attached belongings are included in that removal; when the person is the keeper (or flipped to Keep), the belongings are protected with them. There is no Belongings tray, no separate confirm, no extra count in the status sentence — the sentence counts *people*, and a person's things are part of the person (the Adobe treatment of cast shadows points the same way: parts of a person travel with the person).
- **X9 — The association is visible and correctable in exactly two places.** (a) **Canvas:** an attached belonging's outline is drawn joined to its person's outline treatment (same state colour), so the user can see the bag will go with the man. (b) **The person's chip, when that person is selected/expanded:** a sub-line names the attachments — "Includes: Handbag · Suitcase" — and each named belonging is itself tappable to **detach**: a detached belonging becomes protected (kept, its pixels join the protected set) while its person is still removed; tapping again re-attaches. This is the correction path the brief requires, and it lives where the association is claimed — on the person — not in a separate management screen.
- **X10 — Ambiguity defaults to the keeper's side and to visibility.** Where association is uncertain — classically, a bag *between* the keeper and a removed person — the belonging is **not** silently attached to anyone. It appears as an ordinary object chip in the Distractions group (X2 construction, its object label, default Keep per X3) and no person's chip claims it. The user disposes of it like any object. Silent attachment to the removed person is the one forbidden default: it is how a keeper's bag disappears. **[ASSUMPTION: the tech pass can return an association with a confidence, or a geometric rule (proximity/overlap) whose borderline cases can be surfaced as "unattached". If the pipeline can only return hard attachments with no uncertainty signal, X10 cannot be implemented as written and the fallback is: belongings are included ONLY where the mask is contiguous with the person's — everything else is an object chip. Flagged as OQ3.]**
- **X11 — The protected set, extended (a design requirement on the pipeline).** Protected = keeper persons + their attached belongings + any detached/kept belongings + every kept distraction. The removal must not alter protected pixels — the existing keeper guarantee ("your subject stays untouched", composite from original pixels) extends to the whole protected set, and the verification burden extends with it: the acceptance evidence for this feature must include a keeper-holding-a-bag case and a bag-between-two-people case, or the extension does not ship.

## 5. Rulings — shadows and reflections

- **X12 — Neither is ever an item.** No chips, no canvas outlines, no counts, no toggles — and specifically **no Samsung-style global "erase shadows / reflections" actions**, which contradict per-item review and the keeper guarantee by construction. A removed person's shadow and reflection regions are **mask-expansion responsibilities of that person's removal**, handled server-side as part of the person, exactly as their belongings are (X8). What survives is a failure case for the brush, not a UI element.
- **X13 — What the copy may claim (exact).**
  - **Today's truth, unchanged by this design:** the only shadow sentence in the product is the S5 brush hint ("Paint over anything that should also be removed — including its shadow") — an instruction for the *fix* path that promises nothing about the automatic pass. It stays exactly as is.
  - **Shadows:** no claim is added anywhere — not in S4, not in the S7 summary, not in marketing — until (a) the tech pass confirms shadow expansion beyond the current below-the-feet heuristic, AND (b) blind-test evidence shows it working. Even then, the permitted claim is bounded to the flow where it can be true: the S7 summary may say nothing new (it counts items; shadows are part of a person, X12); a claim, if ever made, belongs in store copy as "shadows are removed with the person" and requires the owner to approve it as a product fact at that time. This doc does not pre-approve it.
  - **Reflections:** **not promised — full stop.** The product historically excluded reflections (brush + warning only), and nothing in this design changes that. If the tech pass lands genuine reflection handling as part of a person's removal, it ships **silently** (X12) under the same evidence bar as shadows before any word is written about it anywhere.
  - **Keeper's shadow and reflection are protected** (X11's set, read with X12): shadow/reflection handling applies only to removed items, never to the keeper — a keeper whose shadow was "helpfully" erased has been touched, and the guarantee says untouched.
- **X14 — The failure path is the brush, and it already exists.** Surviving shadows, reflections, and leftover belongings are precisely what S5 is for; its hint already instructs the shadow case. If reflection handling ships silently (X13), a hint revision ("— including its shadow or reflection") is **proposed, gated on that evidence**, and decided when the evidence exists — not in this doc.

## 6. Consequences for S6, S7, Home — and the saves model

- **X15 — S6:** no layout change. The status line derives from the confirmed job, as it already derives from real state: people-only jobs keep today's line ("Finding people and removing them…"); a job with included distractions reads "Removing @count people and @count distractions…" during its stage. The Home banner copy is item-agnostic ("Cleaning photo in background…") and needs no change.
- **X16 — S7:** the summary line extends only when the job included distractions: "3 people and 2 distractions removed. Your subject stays untouched." Belongings are never itemised (part of their person, X8). The wrong-keeper sheet, compare, and all disclosures are unchanged.
- **X17 — Home demo honesty:** the demo remains a people-only clean and its caption ("Real app output") remains true — it *is* real output, and the demo visually implies people removal only. Standing rule, stated for the future: **a demo asset must be a real output of the shipped pipeline for exactly the capability it visually implies** — a future distractions demo must be a real output of the shipped distractions pipeline, shot for shot.
- **X18 — One job, one save.** Distractions and belongings ride the same job and the same result as the people in that photo; the save is consumed on the saved result as today. Item count never changes what a clean costs. (Composing with the existing saves model; no pricing change is proposed or implied.)
- **X19 — What must NOT be added (the guard list):** no new screens or steps anywhere in the flow; no Settings page of category toggles or detection preferences; no per-item strength, opacity, or "aggressiveness" controls; no global shadow/reflection erase actions (X12); no list-view replacement for the photo on S4; no removal of anything that has not passed S4 review — the analysis may *propose*, only the user *disposes*. If a future idea cannot live inside these rulings, it is a new product decision for the owner, not a design iteration.

## 7. Assumptions and open questions (for the technical pass)

- **OQ1 — Categories:** which distraction categories can the detector actually return, with what per-category precision? X1/X2 need a small closed label set; categories with poor precision should be merged into "Other" or withheld.
- **OQ2 — Confidence calibration:** per-kind confidence distributions, and the show-threshold for distractions (X6) — set from measured precision on a test set, not picked. People's existing band is untouched.
- **OQ3 — Belongings association:** how is "attached" determined (mask contiguity, proximity, a learned association), and can borderline cases be returned as *unattached* (X10)? If not, X10's fallback (contiguity-only inclusion) applies.
- **OQ4 — Shadows:** can mask expansion handle cast shadows beyond the current below-the-feet heuristic (directional cast, shadows on walls/furniture)? This gates any future claim (X13) — design needs the answer, not the mechanism.
- **OQ5 — Reflections:** does any reflection handling exist for a removed person (mirror, window, water, polished floor)? If none: X13's "not promised" is simply the permanent state, and S5 remains the only path.
- **OQ6 — Contract:** the analysis response needs, per item: kind (person / distraction / belonging-of-person-id), category label (distractions), box, confidence, and for belongings a person link + association confidence. Confirm the gateway/worker contract can carry this without breaking Contract v1 clients.
- **OQ7 — Fill quality on thin structures:** wires against sky vs wires against complex backgrounds are different fill problems; the acceptance bar (would-post test) must include both, plus a pole-crossing-the-keeper case for X11.
- **OQ8 — Cost/time:** per-photo processing time and cost with more, larger removal regions on the current CPU stack — if a distractions-heavy job doubles the wait, S6's expectation copy ("~2 minutes") must be re-derived from the new reality before launch, per the standing rule that expectation copy tracks reality.

## 8. Defaults at a glance

| Item | Default state | User's lever |
|---|---|---|
| Background person | Remove (as today) | Tap chip/canvas to keep |
| Keeper (subject) | Protected (as today) | Wrong-keeper flow on S7 |
| Distraction (shown) | **Keep** | Tap to include; group "Remove all" |
| Distraction (low-confidence) | **Not shown** | Brush, if they notice it at all |
| Attached belonging | Follows its person | Detach from the person's chip |
| Ambiguous belonging | Object chip, **Keep** | Flip like any distraction |
| Removed person's shadow/reflection | Handled silently as part of the person | Brush if it survives |
| Keeper's belongings/shadow | Protected, always | — |
